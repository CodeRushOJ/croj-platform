# 里程碑与 Issue 管理

CodeRushOJ 使用跨仓库 Epic 管理产品目标，每个实现 Issue 必须具有唯一责任边界、验收条件、测试证据和目标里程碑。平台仓库记录兼容版本，应用仓库独立开发和测试。

| Milestone | 交付范围 | 退出条件 |
| --- | --- | --- |
| Platform Foundation | Kind、Helm、Compose、Gateway、数据服务、文档、CI 与发版治理 | 全新安装、基础设施 smoke、文档构建、升级和回滚流程可重复 |
| Core OJ | 身份、题目版本、隐藏测试、提交、真实判题、管理端 | 六种语言真实判题与核心 E2E 全绿，不泄露隐藏数据 |
| Contests | ACM/OI、报名、澄清、封榜、重判与可重建榜单 | 竞赛状态机、计分和并发提交验收完成 |
| Community | 论坛、题解、评论、互动、举报、审核与附件 | 权限矩阵、内容净化、审核流和搜索验收完成 |
| v1 Hardening | 性能、安全、无障碍、可观测性、备份恢复与正式发布 | 1000 在线、100 并发提交、20 Judge Job，以及恢复演练全部通过 |

## Issue 生命周期

1. Epic 先定义用户价值、非目标、依赖和退出条件，再拆成可单独回滚的 Issue。
2. Issue 进入开发前必须明确验收条件、DDL/API/安全影响和测试层级。
3. 分支命名使用 `codex/issue-<number>-<short-name>`；提交遵循 Conventional Commits。
4. PR 必须关联 Issue，附测试证据；界面变更附响应式截图，迁移变更附升级与回滚验证。
5. 合并只代表代码完成。只有跨仓库兼容矩阵和目标环境验收通过，Issue 才能关闭。

## 当前 Epic

组织级 Epic 已分别建立在平台、前端、后端、判题服务和沙箱仓库。平台发版 Issue 负责汇总兼容镜像、Chart 版本、迁移顺序、已知限制和回滚入口，不用一个仓库的“完成”替代系统验收。
